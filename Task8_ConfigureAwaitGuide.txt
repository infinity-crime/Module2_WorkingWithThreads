SynchronizationContext - это абстракция, которая описывает как и куда продолжить выполнение (continuation)
после await, если требуется вернуться в тот же контекст. Простыми словами - это механизм, который умеет
планировать выполнение в "особом месте", например в UI-потоке приложения или в контексте веб-запроса.

Возьмем приложения WPF. SynchronizationContext обеспечивает выполнение кода после await (continuation) в 
UI-потоке, чтобы безопасно обновлять элементы управления.

Поведение по умолчанию:
await task; // то же, что await task.ConfigureAwait(TRUE)
-> await захватывает текущий SynchronizationContext, и когда task завершится, его продолжение будет
запланировано обратно через этот контекст.

Что касается .ConfigureAwait(FALSE), то данный метод говорит рантайму не захватывать текущий контекст
и запустить продолжение там, где удобно (обычно это ThreadPool). Из этого идут свои следствия:
1) Уменьшается кол-во переключений контекста (играет на производительности положительно)
2) Устраняет классические сценарии deadlock случаев (когда вызывающий поток заблокирован .Result или .Wait(),
и continuation пытается вернуться в этот же поток).
3) Ну и как раз в БИБЛИОТЕЧНОМ КОДЕ используется ConfigureAwait(FALSE), чтобы не навязывать захват контекста
вызывающему приложению.

Но ВАЖНО то, что .ConfigureAwait(FALSE) не гарантирует, что продолжение выполнится в другом потоке - оно просто
снимает обязательство вернуться в исходный контекст.

Пример с WPF:
--------------------------------------------------------------------------------------------------------------
// В обработчике кнопки (UI-поток)
private async void Button_Click(object sender, EventArgs e)
{
    await Task.Delay(1000); // по умолчанию захватит UI-контекст
    // выполнение продолжения вернётся в UI-поток —> можно безопасно обновлять UI
}
--------------------------------------------------------------------------------------------------------------
ПРИМЕЧАНИЕ: если внутри метода использовать await Task.Delay(1000).ConfigureAwait(false), то 
продолжение выполнится не на UI-потоке, и, следовательно, попытка обновить UI закончится ИСКЛЮЧЕНИЕМ.

Пример deadlock сценария:
--------------------------------------------------------------------------------------------------------------
// Асинхронный метод библиотеки
async Task<string> GetDataAsync()
{
    await Task.Delay(1000); // по умолчанию захват текущего контекста
    return "done";
}

// В коде UI или в синхронном обработчике:
string result = GetDataAsync().Result; // блокирует UI-поток — ожидание результата
--------------------------------------------------------------------------------------------------------------
Здесь deadlock происходит из-за того, что GetDataAsync() завершает Task.Delay() и пытается запланировать
продолжение в UI-контексте, но сам UI-поток заблокирован ожиданием результата -> deadlock.

Решение этой ситуации:
--------------------------------------------------------------------------------------------------------------
async Task<string> GetDataAsync()
{
    await Task.Delay(1000).ConfigureAwait(false); // не захватываем контекст
    return "done";
}
--------------------------------------------------------------------------------------------------------------
Теперь продолжение выполнится на ThreadPool - .Result завершится, deadlock исчезнет. Но лучшей практикой 
является конечно избегать .Result и .Wait().
